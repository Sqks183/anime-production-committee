# 最小经营循环（定稿）

状态：循环结构已定稿（2026-11-21），v2 六接口与状态契约已落入 C++ 核心。当前固定名册、报价、事件和系数是最小纵向切片的暂定参数，不是最终平衡；见 [DATA_MODEL.md](DATA_MODEL.md)、[API.md](API.md) 与 [GAME_RULES.md](GAME_RULES.md)。

## 循环六步与接口映射

循环使用现有六个已实现接口；新局初始化一次，后续企划不重新初始化公司：

| 步骤 | 接口 | 内容 |
| --- | --- | --- |
| 1. 接手企划 | `initialize_game` → `start_project` | 3 个固定报价中选择已解锁项，拨款、工期、目标质量、类型不同；movie 声望 20 解锁 |
| 2. 安排人员与资源 | `apply_decision` | 仅 producing；推进当天前可多次调用、自由调整，不立即扣款 |
| 3. 推进制作 | `advance_day` | 日结消耗资金与时间，产生进度、质量、士气变化；费用不足直接破产，不扣款或推进日/seed |
| 4. 处理制作事件 | `resolve_event` | 仅 event_pending；固定 3 事件、每项 2 个选项，由种子确定性触发 |
| 5. 完成与经营结算 | `calculate_result` | 仅 ended；质量、进度与终局原因决定收入，再结算利润与声望 |
| 6. 重新经营 | 回到 `start_project` | 资金与声望继承，清空企划并重供相同 3 报价，不随机换目录 |

## 每日资源决策与事件取舍

制作阶段推进前调整人员、方针和投入；事件是日结后出现的独立选择，必须先处理才能继续，不是在任意时间调用的第四种制作操作。

1. **工序排班（人放哪）**：前期·分镜演出 → 中期·原画动画 → 后期·摄影合成，下游进度不得超过上游。固定 4 名员工各有擅长工序；技能、擅长和士气影响工作量。上游堵塞时多余工作量丢弃，集中或分配人手的效果由公式决定，不额外设置“堆人质量惩罚”。
2. **当日方针（赶工 / 正常 / 精修）**：影响工作员工的速度、质量和士气消耗；休息按恢复规则处理。新增进度的工序质量低于阈值会返工，质量不是仅在结算时才起作用。排班和方针持续到再次调整。
3. **资金杠杆（外包 / 加班 / 休息）**：外包购买指定工序工作量，当前批次质量固定为 50，不是整体质量打折；加班额外付费、提速、降低工作质量并耗士气。事件概率随当日加班人数增加，没有连续加班计数器。休息（排班为 rest）恢复士气但仍领工资、仍消耗工期，且不能加班。
4. **事件取舍**：日结触发后只能从当前事件选择。现有选项至少涉及资金、工期、质量、士气中的两项；例如购买支援花费 300000 并恢复士气，或协商延期一天但降低中期质量。付费事件计入 spent，支付不足保留待处理事件。

API 中 `apply_decision` 恰有 `assign`、`policy`、`outsource`、`overtime` 四种操作；事件选择用独立的 `resolve_event`。外包和加班以 `enabled` 开关设置今天计划，推进前可撤销；启用时只校验总费用，日结才统一扣款并清除标记。破产短路不执行扣款和日结步骤。

**设计原则：资金、工期、质量、士气相互制约，选择应有代价，目标是避免支配策略。** 这仍需平衡验证，不是已证明的数值结论。计划在推进前可调整，成功日结后不可撤回；事件选择立即生效且不可撤回。

## 一局形态

- 单局 = 一部企划；当前报价工期 20 / 26 / 30 日。5–10 分钟是体验目标，不是实测结论，事件延期或提前完成会改变实际天数。
- 终局三种：完成（completed）/ 截止强制交付或违约（deadline）/ 资金破产（bankrupt），均进入 calculate_result。截止日当天仍可日结；日结后未完成立即结束，不是无限拖到做完。三工序均 100 的完成判定优先于截止判定。
- 同日终局优先于事件并丢弃事件候选，不能靠终局当天新事件再延期。破产不扣款、不推进日期或 seed；其他成功日结（含终局日）只推进一次 seed。
- 结算输出：加权质量分、按预算/质量/平均进度计算且受目标质量与违约影响的收入、利润与声望；超预算额外影响声望。类型没有独立收入乘数，差异体现于报价参数。
- 经济草案：开工 funds += budget；profit = revenue - spent，不含拨款，付费事件也计入 spent。该口径仍待团队复核，前端不能自行改写。
- 下一企划继承资金、声望，同时保留公司日期、seed、员工士气和排班；没有技能成长。新开公司与结算后接取下一部不是同一操作，同种子和相同操作序列可复盘。
- 存档只有单槽本地 GameState v2，拒绝 v1 并提示新开，无迁移。report/result 只在会话展示，重载不恢复历史结算结果。

## 第一版明确不做

招聘解雇（固定 4 人名册）、宣传发行决策、市场模拟、多企划并行、员工成长树、复杂事件库。不影响循环成立，一周工期内不做；也不引入多存档槽、旧版迁移或历史结算持久化。

## 后续平衡与验证

员工技能、士气、方针、外包、每日成本、返工、事件概率和商业评分已有暂定实现，统一集中于 `packages/game-core/include/game_rules.hpp`。精确公式与整数截断见 GAME_RULES，不在 UI 中复制。后续重点是验证完整经营循环、同种子重放、截止/破产边界和策略取舍，并评审拨款与利润口径；不将暂定参数或未执行测试写成定稿结论。
