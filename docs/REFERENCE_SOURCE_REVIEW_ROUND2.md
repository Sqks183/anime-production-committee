# 开源项目源码深读（第二轮）

- 调研日期：2026-11-22
- 调研对象：《动画制作委员会》（Anime Production Committee）
- 调研范围：SimDev、Agency Simulation、SimCorp、econ 的核心源码与部分测试。
- 调研方式：通过 GitHub 读取源码、配置和测试文件；未克隆并运行项目，未执行完整测试套件。
- 本文性质：源码阅读结论与现有设计核对，不是运行时验证，也不构成新增玩法需求或改动既有规则的授权。

## 一、结论摘要

本轮最有价值的不是新玩法，而是模拟系统的正确性与结果可解释性：

1. **SimCorp：周推进与账目记录的工程组织最值得参考。** 将时间推进拆成固定步骤，每笔资金变化有交易类别、金额、余额、关联对象和说明，并通过不变量测试约束结果。
2. **econ：经济规则校验与参数版本对比最值得参考。** 用规则检查、固定随机种子模拟和版本 diff，检查经济循环是否异常，以及一次调参带来了什么变化。
3. **SimDev：阶段结果快照和作品履历值得参考，但源码存在明显实现风险。**
4. **Agency Simulation：项目机会、合同条件和现金流表达值得参考，但其账务实现存在预付款重复计算等风险。**

**对本项目的总建议：不增加玩法系统。** 优先确保周推进唯一且顺序固定、资金变化可追溯、作品结算不重复、阶段与重大事件能进入作品履历，并用固定场景回归验证规则。

## 二、逐项目源码观察

### 1. SimDev — 阶段推进、员工与作品结算

仓库：[SuitedTom/SimDev](https://github.com/SuitedTom/SimDev)

阅读文件：
- `js/systems/developmentSystem.js`
- `js/systems/gameState.js`
- `js/systems/staffSystem.js`
- `js/systems/reputationSystem.js`
- `js/main.js`

**观察到的设计**
- 项目开发被拆为 Planning、Development、Testing、Release 阶段。
- 阶段结束时尝试保存阶段数据，发布时再汇总作品质量、成功度、收益、缺陷和受众反馈。
- 项目阶段、员工、公司状态与作品评价处于同一经营循环。

**可借鉴**
- 阶段结束时保留阶段结果快照，避免最终结算只剩一个无法解释的总分。
- 作品结算可汇总阶段表现、重大事件和关键结果，形成可回看的作品履历。

**源码风险**
- `advanceTime()` 中 `actualCost` 声明为 `const` 后又执行 `actualCost += salaries`；存在员工时会触发赋值错误。
- 周推进与员工处理函数都可能修改项目阶段进度，存在重复计算风险。
- 随机事件/开发风险直接使用 `Math.random()`，没有统一随机数入口。
- 阶段推进存在多套处理函数，规则校验与实际推进不完全统一。
- 部分指标直接随机生成，不能作为可靠结算依据。

**对本项目的落点**
- 本项目已有五个制作阶段和周制，不增加阶段。
- 只需确保阶段结束保存必要结果，最终结算能够回溯结果形成过程。
- 阶段推进应只有一个权威入口；员工、项目与时间系统不得重复推进同一进度。

### 2. Agency Simulation — 项目机会、合同与现金流

仓库：[banyapon/agency-empire](https://github.com/banyapon/agency-empire)

阅读文件：
- `media/main.js` 中项目机会、接受项目、员工分配、项目进度、账单与付款、每日推进相关逻辑。

**观察到的设计**
- 项目机会包含预算、工期和付款方式。
- 接受项目后进入制作，项目完成后生成账单，再按计划回款。
- 项目制作与公司日常工资、运营支出共同影响现金余额。

**可借鉴**
- 玩家接受项目前应能看清承担成本、合同收益和付款条件。
- 项目完成与现金到账可以作为不同财务事件表达。
- 结算时区分合同收入、制作成本和其他来源，比只显示余额变化更容易理解。

**源码风险**
- 项目进度主要由工期和分配人数决定，没有真正体现员工能力差异。
- 资金不足时工资逻辑主要记录通知，没有完整处理欠薪或后续状态。
- 接受项目时扣除预付款，但生成账单仍按完整预算分期，存在预付款重复计算风险。
- 项目进度、付款和随机事件集中写在大型主文件中，扩展性有限。

**对本项目的落点**
- 承制路线明确区分合同收益与项目成本；委员会路线明确区分投资支出、商业收益和分账。
- 保留现有结算模型，不新增独立账单、预付款或分期回款玩法。
- 界面显示应与现有规则一致，不得因参考项目而擅自改变合同收益口径。

### 3. SimCorp — 确定性推进、资金流水与测试

仓库：[Splortch/Simcorp](https://github.com/Splortch/Simcorp)

阅读文件：
- `backend/simcorp/engine/simulation.py`
- `backend/simcorp/engine/db.py`
- `backend/tests/test_simulation.py`
- `backend/tests/test_workforce.py`

**观察到的设计**
- `advance_day()` 将推进过程拆成固定顺序：推进日期、支付工资、偿还贷款、推进研发项目、计算营销效果、生产商品、市场需求与销售、支付固定运营费用、更新声望、生成财务快照并检查胜负。
- 资金通过统一的 `record_transaction()` 记录交易类别、金额、交易后余额、关联对象 ID 和说明；余额可由最近流水的 `balance_after` 追溯。
- 测试覆盖初始状态、推进交易、余额与最后流水一致、库存不为负、资金不足停止生产并告警等情况。

**可借鉴**
- 时间推进应有单一入口和固定步骤顺序，每项结算只执行一次。
- 资金变化应保留来源、关联对象和理由，便于核对。
- 对余额一致性、禁止重复结算、资源不能非法为负等规则写成自动化测试。

**边界**
- 这里是带余额记录的现金流水账，不应描述成完整复式记账系统。
- SQLite、制造业库存、贷款偿还和 AI 员工管理与本项目当前范围不符，不直接迁移。

**对本项目的落点**
- 明确每周工资、固定支出、疲劳/士气、项目进度、事件检查和作品结算的先后顺序。
- 每笔收入/支出记录类型、金额、关联企划/作品或员工、原因。
- 对作品只能结算一次、收益不得重复入账、未完成作品不能最终结算等不变量增加测试。

### 4. econ — 经济规则校验与参数差异分析

仓库：[samw3/economy](https://github.com/samw3/economy)

阅读文件：
- `src/econ/economy.py`
- `src/econ/lint/rules.py`
- `src/econ/lint/runner.py`
- `src/econ/lint/diff.py`
- `src/econ/sim/engine.py`
- `tests/test_lint_sim_lean.py`
- `docs/FORMAT.md`

**观察到的设计**
- 使用 YAML 描述经济规则，并对配置、引用、公式与经济循环进行静态检查。
- 检查项包括 money-pump（无风险/成本的无限赚钱循环）、risk-reward-inversion、成长速度偏离和货币上限等。
- 支持固定随机种子的模拟、关键指标输出，以及比较参数版本前后的 findings 和模拟指标。
- 使用线性规划寻找经济循环，并尝试通过 Lean 4 证明部分性质。

**可借鉴**
- 经济规则不仅要检查单笔计算是否正确，也要检查是否存在反复操作后凭空获利的路径。
- 固定随机种子运行代表性经营场景，便于复现和比较。
- 参数调整前后比较成本、收益、声望、员工状态和经营结果，避免只凭主观感受调数值。
- 将已发现的异常路径固化成反例测试。

**边界**
- 其模型面向 RPG 经济，不能直接套用到承制、委员会投资、周制制作和商业分账。
- Lean 4 工具链和 RPG 专用公式不适合本项目首版，维护成本可能超过收益。
- 本轮是源码阅读，未运行其 linter 或模拟器验证实际输出。

**对本项目的落点**
- 适配本项目自身的合同收益、制作成本、投资风险、商业收益与分账规则。
- 先从参数集中配置、固定场景模拟和版本对比做起，不引入复杂证明工具链。

## 三、对本项目的建议清单

| 优先级 | 建议 | 目的 | 是否改变玩法 |
|---|---|---|---|
| P0 | 明确唯一的周推进入口与固定结算顺序 | 避免重复扣款、重复推进、事件检查顺序不一致 | 否 |
| P0 | 资金变化保留来源、关联对象和结算理由 | 让玩家和开发者能追溯余额变化 | 否 |
| P0 | 作品结算只允许发生一次，未完成作品不能最终结算 | 防止重复收益和非法状态转换 | 否 |
| P1 | 阶段结束保留必要结果，重大事件进入作品履历 | 让最终评价可回溯 | 否 |
| P1 | 建立固定经营场景回归测试 | 覆盖正常经营、资金紧张、制作延期、作品成功和失败 | 否 |
| P1 | 参数调整前后输出关键指标差异 | 降低数值调整的盲目性 | 否 |

### 固定场景建议

以下是验证场景，不是新增游戏玩法：

1. 正常经营：资金、工资、项目进度和周推进均按预期变化。
2. 资金紧张：资金不足时按既有规则处理，不出现负数或重复扣款。
3. 制作延期：项目进度、员工状态、延期影响和事件记录保持一致。
4. 作品成功：结算收入、成本、评价和声望变化各发生一次。
5. 作品失败：损失、评价和声望变化按既有规则结算，不重复触发。

## 四、明确不采用的内容

- 不增加 SimDev 的科技树或复杂开发决策。
- 不增加 Agency 的独立账单、预付款或分期回款玩法。
- 不引入 SimCorp 的完整制造业财务、贷款、库存和 AI 员工管理系统。
- 不引入 econ 的 Lean 4 证明工具链或 RPG 专用经济公式。
- 不引入真实动画制作软件中的任务协作、云盘、多人评论和审核平台。

## 五、调研边界与后续工作

本轮完成的是四个仓库的定向源码阅读，阅读范围如各项目章节所列。没有克隆并运行项目，也没有执行完整测试套件。因此，本文区分了源码中可直接观察到的实现方式与根据代码推断的风险；不能据此宣称这些项目当前运行无误或测试全部通过。

下一轮可继续检查：
- AnimeStudioSimulator：最贴近动画公司经营题材，重点核对模型边界、项目/作品/员工/财务关系。
- numeric-kit：重点核对参数表、模拟场景、覆盖率和调参提案工作流；注意其框架 Excel 不在仓库。
- Animation Workflow Manager：重点核对场景、任务、人员、素材、审核状态与操作日志之间的关系；只抽取经营游戏所需的轻量概念。

继续调研的产出仍应是参考与风险报告，不直接变成新增需求。是否采纳由项目负责人结合当前仓库和首版范围决定。
