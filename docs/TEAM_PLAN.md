# 本轮分工（V1.0 迁移）

状态：2026-11-21 · 基线 `main@94be77a` · 对应议题 [#1](https://github.com/zhengmin486/anime-production-committee/issues/1) 与 #2–#9。

## 一句话现状

`main` 上跑通的是**旧切片**：按天推进、三工序、固定 4 人、3 个报价、3 类事件。技术链路没问题——C++ 算规则、WASM 过桥、React 只展示，这套保留。

《游戏设计总案 V1.0》要的是**周制经营**：每周推进、五阶段制作、4 个企划轮换、承接制作或参与委员会、六项专业能力、十年后结算公司成败。

所以这轮不是「在现有玩法上加功能」，而是**先把规则和数据结构换掉，再往上补玩法**。在旧规则上继续堆功能（比如给日推进加新事件、给三工序加新特效）会全部作废。

## 顺序：M0 先冻结，谁都不能绕

M0（#2 契约冻结）没完成之前，核心和前端**都不许改契约字段、C++ 状态结构、存档版本**。原因是状态结构一改，后端计算、前端界面、存档格式三处要一起返工，改一次就是三份工。

## 三条不许破的线

1. **账目口径按总案 §5.4 / §5.5，不许自己发明。** 制作合同预算属于项目总投资，不是额外收入；投资本金只扣一次；商业收入按投资比例分，不先回收本金。现在代码里「现金涨 922 万、利润显示 122 万」就是口径没定清的后果，不要再加第三种算法。
2. **待定数值集中放 `game_rules.hpp` 并标 `TODO(待定)`。** 不许散进前端组件，也不许自己拍板平衡值。总案 §12 列了几十项待定，那些是留给负责人拍的，不是留给实现者猜的。
3. **文件所有权不越界。** `game_rules.hpp` / `game_core.cpp` / 核心测试归核心负责人；`apps/web/src/types/`、`test/fixtures.ts`、`scripts/browser.test.mjs` 归契约负责人；页面归前端。两个人要改同一文件，先拆文件边界再动手。

## 怎样算做完

每个议题末尾都有验收清单，共同的几条：

- 真实 WASM 跑过，不是 TypeScript 模拟。
- 命令和输出贴在 PR 里；没跑就写「没跑」，不要写「应该没问题」。
- 前端不重算规则数值，显示值全部来自核心回执。
- 文档跟着改：规则变化进 `GAME_RULES.md`，协议变化进 `API.md` / `DATA_MODEL.md`，不允许文档领先于实现。

## 认领方式

在对应议题下评论，模板见 [CONTRIBUTING.md](../CONTRIBUTING.md#认领拆分与完成标准)。负责人确认文件边界后设置 Assignee 与评审人，再从最新 `main` 建短期分支。一个 PR 对应一个可验收任务。
