# M3 多项目经营跨模块手算 Fixture

> 状态：集成验证样例，不是员工/供应商数值平衡基准
> 日期：2026-11-26
> 依据：DEVELOPMENT_ROADMAP M3、DOMAIN_ARCHITECTURE §§5.2/5.4/5.6/7.4/9、DEC-PLAY-001/002/003/004、DEC-STAFF-001、M0_CONTRACT_FREEZE INV-09/10/19/20/27/28
> 用途：验证多项目资源竞争、工作项磨合、供应商共享产能、企划来源和项目终止隔离。
>
> 本文只定义少量关键场景。数值仅用于构造可手算输入，不代表产能平衡参数。模块内部算法由 Staff/Vendor/Market/Rules Kernel 负责人实现。
>
> **通用初始前提：** 每个 `producing` 项目都有一名通过任职资格校验且已分配到该项目的监督（INV-27）。除特别说明外，被重新分配的员工不承担监督岗位；若测试监督更换，必须先准备原子 Swap/Replace，不能留下监督空缺或重复。

## 1. Fixture A：核心员工严格单项目归属

### 初始状态

- 公司处于 running。
- Project A、Project B 均为 producing。
- 员工 S 是核心员工，职业能力同时适配 A、B 的某个已解锁工作项；S 不是 A 或 B 的监督。
- S.assignment_work_id = A。
- A、B 均有可由 S 承担的工作项需求。

### 验证步骤

1. 执行一次周结算，观察 A、B 的分配结果。
2. 将 S 的归属改为 B，再执行相同输入的周结算。
3. 对相同状态分别采用 A→B、B→A 的项目遍历顺序计算。

### 预期结果

- 第一次结算中，S 只能进入 A 的产能分配；B 不得获得 S 的任何产出。
- 归属改为 B 后，S 只能进入 B；不得保留 A 的隐式支援份额。
- 不存在工时切片、双项目归属或 Kernel 私自决定员工跨项目分配。
- 相同状态与命令序列仅改变项目遍历顺序，最终状态与结算结果不变。

**规则边界：** 玩家决定员工→项目归属；Kernel 只在项目内部确定员工→工作项分配。多项目竞争不是自动把一个员工拆成两份。

## 2. Fixture B：工作项级一次性磨合损失

### 初始状态

同一项目包含两个可分配工作项：

| 工作项 | 初始进度 | 已有贡献者 | 新接手员工 |
|---|---:|---|---|
| Item A | 已有有效产出 | Staff Old | Staff New 从未参与 |
| Item B | 0 | 无 | Staff New |

Staff New 具备两个工作项所需能力，并被合法分配到该项目。

### 验证步骤

1. 本周由 Staff New 接手 Item A 与 Item B。
2. 对 Item A、Item B 分别计算本周有效产出。
3. 在后续周继续由 Staff New 承担 Item A，观察磨合惩罚是否重复。
4. 再换一个从未参与 Item A 的员工接手，观察是否按新的接手关系重新判定。

### 预期结果

- Item A 已由其他员工开工，且 Staff New 从未参与过该项：按 DEC-STAFF-001 触发一次性个人工作量效率损失。
- Item B 尚未开工：不触发磨合损失。
- 磨合损失只影响工作量，不影响质量。
- 同一员工对同一工作项的一次性损失不得每周重复扣除。
- 判定依据是具体 WorkItem 的既有贡献记录，不得用“同一集任意工作项已有产出”代替。

## 3. Fixture C：同一供应商跨项目共享产能

### 初始状态

供应商 S 的 capacity_per_week = 100。

| 合同 | 项目 | 状态 | weekly_cap |
|---|---|---|---:|
| Contract A | Project A | active | 60 |
| Contract B | Project B | active | 40 |

### 验证步骤

1. 创建以上两个合同。
2. 尝试再创建一个 weekly_cap = 1 的 active 合同。
3. 将 Contract A 标记为 delivered 或 failed 后，再尝试签订新合同。
4. 另建一个独立子场景：在 Project A 下创建两个 `weekly_cap = 20`、指向同一已解锁 WorkItem 的 active 合同，确认其 `work_id/item_id` 一致；此时 Contract B 仍占用 40，总承诺产能为 80，不超过 100。
5. 对第 4 步的两个合同检查累计交付边界。

### 预期结果

- 初始 active 承诺总量为 100，恰好达到供应商容量。
- 第三个合同必须因产能不足失败；失败不得留下合同、Finance 流水或部分占用。
- Contract A 不再 active 后，其 60 周产能释放；新合同可在剩余容量范围内签约。
- 第 4 步的两个合同属于同一 Project 的同一 WorkItem，可由内部产能共同推进，但累计交付不得超过 work_total；超出部分不产出、不退款。
- 容量按供应商全公司范围汇总，不得按 Project 分别计算出两份完整容量。

## 4. Fixture D：一个项目终止，不污染其他项目

### 初始状态

- Project A、Project B 均为 producing。
- 两个项目分别有独立的员工归属、工作项、外包合同。
- 同一供应商的 active 合同总周产能未超过容量。
- B 有自己的正常计划与待推进工作项。

### 验证步骤

1. 对 Project A 执行 abort_work(A)。
2. 检查 A 的人员归属、外包合同状态、供应商可用产能和 Finance 扣罚流水。
3. 检查 B 的人员归属、外包合同、工作项进度与计划。
4. 再推进 B 所在周，确认 B 正常结算。

### 预期结果

- A 按中止契约终止；A 的人员占用释放，未完成外包合同按规则进入终止状态并释放供应商产能。
- A 的扣罚只进入 Finance 一次，项目归因正确。
- B 的人员、合同、计划、工作项和事件不被 A 的终止操作清理或覆盖。
- A 不再作为 producing 项目参与后续分配；B 仍可正常推进。
- 任何一步失败都不能留下半终止状态。

## 5. Fixture E：企划槽提供真实项目来源

### 初始状态

- 新游戏 Market 槽位为 4 个。
- 槽位上限为 10。
- 至少存在两个合法 Offer，且各自可实例化为合法制作蓝图。
- 玩家拥有满足开工要求的资金与资格。

### 验证步骤

1. 从 Market 选择 Offer A 开工。
2. 再从 Market 选择另一个合法 Offer B 开工。
3. 检查两个 Project 的 OfferSnapshot、蓝图实例化结果与 Market 消费状态。
4. 对一个符合条件的 Offer 执行一次 lock_offer，在有效锁定期内开工并检查定金抵扣。
5. 检查过期 Offer 与已消费 Offer 是否可被再次开工。

### 预期结果

- 两部作品来自正常 Market Offer，不是测试代码直接拼装 Project。
- 每部 Project 在立项时冻结自己的 OfferSnapshot；后续 Market 刷新或模板变化不影响已开工项目。
- Offer 被消费后不得重复立项；企划 ID 终身唯一。
- 锁单遵循 M0 §14.13：终身一次，锁定覆盖 W/W+1，W+2 周初失效，到期定金不退；有效期内开工抵扣已付定金，不重复计支出。
- 市场槽初始数量与上限遵循 M0/Market 契约，不在集成层自行扩容。

## 6. M3 统一验收关注点

以上 Fixture A–E 证明跨模块边界；M3 里程碑还需要独立完成路线图要求的 520 周压力验证。

长跑重点观察：

- 核心员工始终只有一个项目归属；
- 同一供应商 active 合同周产能不超容量；
- 项目交付/中止不遗留错误活动引用；
- Finance 余额与流水恒等式持续成立，正常经营余额不为负；
- 多项目遍历顺序不改变结算结果与坐标随机结果；
- 事件 pending 与项目生命周期一致；
- 存档检查点可恢复并继续得到可复现结果。

## 7. 最小验证集

不机械扩展排列组合。进入运行时后，至少验证：

1. Fixture A：单项目归属与遍历顺序无关。
2. Fixture B：已开工工作项触发一次性磨合，未开工工作项不触发。
3. Fixture C：跨项目供应商容量不能超卖，终止合同释放容量。
4. Fixture D：一个项目中止不污染另一个项目。
5. Fixture E：两个项目由正常 Market Offer 启动，Offer 消费与锁单抵扣正确。

520 周长跑是 M3 阶段出口验证，不要求每个模块 PR 重复执行。
